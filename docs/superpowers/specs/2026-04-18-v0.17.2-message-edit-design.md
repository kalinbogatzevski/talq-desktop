# v0.17.2 Design — Message edit

Date: 2026-04-18
Status: approved, ready for planning
Author: Kalin (with Claude)

## Summary

Nextcloud Talk lets users edit their own messages within a ~6-hour window. The server parses the edited body, rewrites stored content, and echoes back the updated message object with `lastEditActorId` + `lastEditTimestamp` fields so all clients can render an "(edited)" marker. TalQ already **renders** received edits correctly (since `Message::fromJson` falls through to whatever fields are present), but it has no **compose** path: there's no Edit context-menu action, no editing bar, no API call. This spec adds the missing compose path.

The design mirrors the existing reply-bar pattern in `ComposerWidget` for UI, and the existing `deleteMessage` pattern in `MessageListModel` for the API call.

## Scope

**In scope:**
- Edit own text messages via right-click context menu.
- Inline editing bar in the composer (similar to the existing reply bar).
- Server-enforced edit window — we don't pre-filter client-side; if the server rejects, we surface the error.
- "(edited)" marker in the chat render once `lastEditTimestamp` is populated.
- Clear editing state on conversation switch or Esc.

**Out of scope:**
- Editing messages with file attachments (NC Talk server itself doesn't allow this; we just don't show the Edit item on those).
- Edit history UI (NC Talk web doesn't expose it either).
- Message deletion/edit moderation for other users (admin/mod flows — separate feature).

## Section 1 — Server API + Model

### API call
Endpoint:
```
PUT /ocs/v2.php/apps/spreed/api/v1/chat/{token}/{messageId}
Content-Type: application/json
Body: { "message": "<new text>" }
```

Success response (OCS 200): the updated message object, including the new `lastEditActorId` and `lastEditTimestamp` fields. On failure (past window, no permission, attachment message, network) the server returns 4xx; the existing `ApiClient::put` already surfaces this through its `Callback` with `success=false` and the server's error message.

### Message model field
Add to `src/models/Message.h`:

```cpp
qint64 lastEditTimestamp = 0;  // 0 = never edited
QString lastEditActorId;       // populated when lastEditTimestamp > 0
```

In `src/models/Message.cpp::fromJson`, read:

```cpp
m.lastEditTimestamp = json["lastEditTimestamp"].toInteger();
m.lastEditActorId   = json["lastEditActorId"].toString();
```

### Model method
Add to `src/models/MessageListModel.{h,cpp}`:

```cpp
Q_INVOKABLE void editMessage(int messageId, const QString &newText);
```

Implementation (pattern matches the existing `deleteMessage`):
1. Find the message in `m_messages` by id — bail if not found.
2. Build the path `"/apps/spreed/api/v1/chat/" + m_token + "/" + QString::number(messageId)`.
3. Call `m_api->put(path, QJsonObject{{"message", newText}}, callback)`.
4. In the callback:
   - On success: parse `data.ocs.data` as a `Message`, replace the local entry at the same index, emit `dataChanged(...)` for that row so `ChatPainter` redraws.
   - On failure: `emit errorOccurred(...)` with the server's message (existing signal, already routed to UI).

The server's response echo arrives both via this direct HTTP callback AND via the chat poller (`/chat/{token}?lookIntoFuture=1`); the poller path will notice the new `lastEditTimestamp` and update again if it gets there first. Idempotent either way.

## Section 2 — Composer editing bar

### Widget changes in `src/ui/ComposerWidget.{h,cpp}`

The existing reply bar is a small `QWidget` sibling of `m_input` that shows a preview + cancel button. Mirror that for an **edit bar**:

```cpp
// Header (new public methods):
void showEditingBar(const QString &originalText);
void hideEditingBar();

// Header (new signal):
void editMessageRequested(const QString &newText);
void editingBarCancelled();

// Private members:
QWidget *m_editingBar = nullptr;
QLabel  *m_editingPreview = nullptr;
bool     m_editing = false;
```

Visuals: a thin bar above `m_input` with a pen glyph (✏️), a single-line preview of the original text, and a ✕ close button — same layout/style as the existing reply bar (reuse `PainterTheme` colors so it matches).

### Behavior

**Entering edit mode** (driven by `MainWindow`):
- `showEditingBar(original)`:
  - Sets `m_editing = true`.
  - Populates the preview label with the original text (single-line, elided at the end).
  - Replaces `m_input` contents with `original` (plain text; any rich-object placeholders have been resolved by `Message::fromJson`, so we use the post-resolution body via a stripped-HTML plain-text version).
  - Moves the input cursor to the end.
  - Sets focus on `m_input`.
  - Shows the editing bar (hides the reply bar if somehow visible — editing and replying are mutually exclusive).

**Sending while editing**:
- The existing Enter-to-send path in `ComposeTextEdit::keyPressEvent` calls `ComposerWidget::trySend()` (or equivalent). That method checks `m_editing`:
  - If editing: emit `editMessageRequested(currentText)` and hide the editing bar.
  - Otherwise: emit the existing `sendMessage(text)` signal.

**Cancelling**:
- `hideEditingBar()`: sets `m_editing = false`, clears the input, hides the bar, emits `editingBarCancelled()`.
- Triggered by: the ✕ button, Esc when the input has focus and the bar is visible, or externally (MainWindow on conversation switch).

### Edge cases
- **Empty edited text**: if the user clears the composer and hits Enter, treat as no-op (don't send an empty edit). The existing `sendMessage` path already guards against empty text; reuse the same check.
- **Switching rooms mid-edit**: the conversation-switch reset already wired for mention popups in v0.17.1 is extended to also call `hideEditingBar()` and clear `m_editingMessageId` on `MainWindow`.
- **Esc key**: `ComposeTextEdit::keyPressEvent` adds an `if (m_owner->m_editing) { m_owner->hideEditingBar(); return; }` arm. Doesn't interfere with the reply bar's Esc (they never coexist).

## Section 3 — Entry point + wiring

### Context menu item (`src/ui/MainWindow.cpp`)

In the message-context-menu builder (around the `if (isOwn)` block that currently holds the Delete item), add an Edit item above Delete:

```cpp
if (isOwn && !hasFile) {
    menu->addAction(QStringLiteral("\u270F\uFE0F  Edit"), this, [this, msgId, msg]() {
        m_editingMessageId = msgId;
        // Use the plain-text body (strip HTML from resolved message body).
        QString plain = plainBodyText(msg);
        m_composer->showEditingBar(plain);
    });
}
```

`hasFile` gate: the server won't let you edit file-share messages, so hide the action client-side. Read it from the same `msg` variant the menu lambda already has (`msg.value("hasFile").toBool()`).

`plainBodyText(msg)` is an existing helper in MainWindow used by the selection-mode copy and forward actions (uses `QTextDocument` to strip HTML from `messageText`). Reuse it verbatim.

### Signal wiring (`src/ui/MainWindow.cpp::buildChatPage()`)

Alongside the existing `m_composer` connections:

```cpp
connect(m_composer, &ComposerWidget::editMessageRequested, this,
        [this](const QString &newText) {
    if (m_editingMessageId <= 0) return;
    m_messages->editMessage(m_editingMessageId, newText);
    m_editingMessageId = 0;
});

connect(m_composer, &ComposerWidget::editingBarCancelled, this, [this]() {
    m_editingMessageId = 0;
});
```

### Conversation-switch cleanup

The existing `conversationTokenChanged` handler in `ComposerWidget::setMessageModel` (added in v0.17.1 for mention popup reset) is extended to call `hideEditingBar()` as well. `MainWindow` also nulls `m_editingMessageId` in its own token-change listener (the `onConversationSelected` path, or the existing home-navigation lambda).

### Optimistic UI (optional — defer if scope creeps)

The initial implementation does NOT update the bubble text locally before the server echo arrives. The round-trip is fast (<100 ms on LAN), so the ~1 frame delay before the new text appears is acceptable. If user testing shows this feels laggy, add an optimistic update: patch the local Message immediately, revert on failure.

## Section 4 — "(edited)" marker in ChatPainter

In `src/painter/ChatPainter.cpp` where the time label is drawn (search for the `timeString` or similar variable used in `paintOwnMessage`/`paintOtherMessage` to draw the HH:MM label), prepend `(edited) ` when `ml.lastEditTimestamp > 0`:

```cpp
QString timeLabel = ml.lastEditTimestamp > 0
    ? QStringLiteral("(edited) ") + ml.timeString
    : ml.timeString;
```

Route `lastEditTimestamp` onto `MessageLayout` (add field) and populate it in `LayoutEngine::computeLayout` from the `Message` object, same pattern as existing fields.

Styling: no change — uses the same muted-text color as the timestamp. No extra line, no icon, no visual weight. Matches NC Talk web.

## Verification (manual)

- Right-click an own text message → "Edit" is visible; right-click a received message → no "Edit".
- Right-click an own file-share message → no "Edit".
- Pick Edit → editing bar shows above composer with the preview; composer pre-filled with the original text; focus on composer.
- Modify text, hit Enter → message in the chat view updates within ~1s; `(edited)` appears prefixed to the time.
- Other clients (web, second TalQ instance) also see the update + the `(edited)` marker.
- Click ✕ on the editing bar → bar hides, composer clears.
- Hit Esc while editing → same as ✕.
- Switch conversation mid-edit → editing bar hides, state clears; returning to the original conversation shows a clean composer.
- Try editing a message older than ~6 hours → server returns 4xx; an error toast appears; the editing bar stays visible so user can cancel or try again.
- Type `@user` while editing → mention popup still works (composer autocomplete is orthogonal to editing state).
